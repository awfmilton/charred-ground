# Charred Ground architecture

The runtime lives in `index.html`. Three.js r128 and PeerJS 1.5.4 load from CDNs. UI styles and game code are inline; audio is synthesized through one AudioContext.

- **Simulation:** fixed-step ballistics with wind and selectable boundaries. A data-driven registry routes payloads, equipment, structures and drones. The world spans 480 meters; its 481-sample heightfield is extruded into a 160-meter-wide indexed terrain mesh.
- **Rendering:** terrain vertices and normals change only on dirty frames. Particles use a 400-slot buffer; shells, trees and rocks use instancing. Trails use a bounded buffer and expire after impact. Water uses a lightweight animated shader. Removed entity meshes dispose their geometry/materials.
- **Camera:** tactical overview, tank focus, gunner optics and orbital exploration share one perspective camera. Orbit, tilt, zoom and pan are local presentation state. A 3D shot begins with a short tank-side launch camera and returns to tactical framing; projectile height expands the view. Solid trails show sampled flight history; dashed arcs estimate the remainder.
- **Multiplayer:** PeerJS host-authoritative snapshots carry terrain, combat, inventory and shop state. The host validates ownership and turn order for commands. Camera state and API keys are never broadcast. Disconnected guests become bots; host migration is not implemented. The Charred room prefix separates the enlarged-map build from the older release.
- **AI:** local numerical targeting works without a key. Optional Gemini JSON decisions are validated and time out after three seconds. Keys stay in page memory and go only to Google's API.

## Player accounts & API

The application server (`scripts/serve.cjs`) serves `index.html` and delegates `/api/*` requests to `scripts/api.cjs`, backed by `scripts/auth.cjs` and the SQLite data-access layer in `scripts/db.cjs` (`node:sqlite`).

- **Module boundaries:** `scripts/serve.cjs` handles HTTP listener lifecycle and static root routing; `scripts/api.cjs` enforces request validation, rate limits, authentication cookies/bearer tokens, OAuth provider handshakes, profile limits, and match attestation rules; `scripts/auth.cjs` encapsulates salted `bcryptjs` password hashing, 6-digit email verification codes, RFC 6238 TOTP (HMAC-SHA1), session token hashing, and OAuth 2.0 provider metadata; `scripts/db.cjs` isolates all SQLite queries behind a `DataStore` interface so a managed database can replace SQLite without changing route handlers.
- **Tamper-proof match attestation:** Before a round begins, the authenticated host requests a single-use match ticket (`POST /api/matches/start`) recording the participant roster and issuing a cryptographic nonce. When the round finishes, every authenticated human participant submits their signed/authenticated outcome and action log (`POST /api/matches/:id/attest`). The server verifies roster membership, single-use nonce validity, elapsed duration bounds, weapon allowlist membership, finite aiming parameters, and kill-count conservation, and computes a canonical outcome digest. Leaderboard wins, kills, and match counts are committed only when every human participant in a multi-human match submits a matching canonical digest. Single-human vs AI matches are recorded as `bot_match` in personal history and never increment public leaderboard wins.
- **Client state isolation:** Camera state (`viewMode`, `orbitYaw`, `orbitPitch`, `orbitZoom`, `exploreX`, `exploreZ`) and external API keys (`#apiKey`, TURN credentials) never leave the client in peer snapshots or `/api/*` payloads.

The Sites deployment retains its existing project identity. Hosting credentials, local deployment archives, temporary scripts and account configuration are deliberately not stored in this repository.
